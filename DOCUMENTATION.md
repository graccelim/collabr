## 1. What is collabr.

### Plain English

collabr. is a two-sided marketplace that connects content creators directly with brands for paid and barter collaborations. A brand posts a campaign brief describing what content they need. Creators browse open campaigns and apply with a pitch and optional rate. The brand reviews applicants, selects one or more, and pays via an escrow system — funds are held until the brand confirms the creator's live post is up. At that point funds are automatically released to the creator.

The platform eliminates the need for PR agencies or talent management intermediaries. Brands pay a 12% platform commission (8% on the Pro plan). Creators receive their payout directly.

### Who the two user types are

**Brands** — Singapore-based businesses, typically SMEs. They post campaigns, review applicants, pay via escrow, review content, and confirm live posts to release payment. Brands can be on a free or pro plan.

**Creators** — Singapore-based nano and micro influencers (1k–200k followers) on Instagram, TikTok, and YouTube. They apply to campaigns, submit content drafts for brand review, post live, and submit their post URL to trigger payment.

There is also an **admin** role for platform staff to manage disputes.

### What problem it solves

Traditional influencer marketing requires brands to either engage expensive PR agencies ($2,000+/month retainer) or manage creator relationships manually with no payment protection. collabr. provides a self-serve platform with:
- Verified creator stats (follower counts)
- Structured content review workflow
- Stripe escrow that protects brands from non-delivery and creators from non-payment
- Two-way ratings that surface quality creators and responsible brands

### Market

Singapore, targeting local SMEs and nano/micro creators. All amounts are in SGD. The platform is in beta — free to use while establishing the creator and brand base.

### How Supabase auth works

Authentication uses Supabase's SSR library (`@supabase/ssr`) which stores the session in HTTP-only cookies. This means session state is available on the server and does not rely on localStorage.

**Two Supabase clients exist:**

```typescript
// lib/supabase/client.ts — browser client (client components)
import { createBrowserClient } from '@supabase/ssr'
createBrowserClient(SUPABASE_URL, SUPABASE_ANON_KEY)

// lib/supabase/server.ts — server client (server components + API routes)
import { createServerClient } from '@supabase/ssr'
// createClient() — uses anon key, reads/writes cookies
// createAdminClient() — uses SERVICE_ROLE_KEY, no cookies, bypasses RLS
```

**When to use which:**

| Client | Where used | RLS | Use case |
|---|---|---|---|
| `createBrowserClient` | Client components (`'use client'`) | Enforced | Profile edits, boost purchase, realtime |
| `createClient()` (server) | Server pages, API routes | Enforced | User-facing reads and writes |
| `createAdminClient()` | Cron jobs, signup route, admin pages | **Bypassed** | Initial row inserts, bulk reads, admin dispute resolution |

The `createAdminClient()` uses the `SUPABASE_SERVICE_ROLE_KEY`. It must never be exposed to the browser. It is used in:
- `app/api/auth/signup/route.ts` — to insert the initial `users` and `brand_profiles`/`creator_profiles` rows before the session cookie is set
- All cron jobs — since cron requests have no user session
- `app/(dashboard)/admin/disputes/*.tsx` — to read all disputes (admin bypasses party-restricted RLS)
- `lib/notifications.ts` — to insert notifications on behalf of other users

### How middleware.ts protects routes

The middleware runs on every non-static request (excludes `_next/static`, `_next/image`, `favicon.ico`, and image files). On every request it:

1. Creates a `createServerClient` instance with cookie passthrough
2. Calls `supabase.auth.getUser()` — this refreshes the session token and writes updated cookies to the response, keeping sessions alive
3. If the route is in `PROTECTED_PREFIXES` and there is no authenticated user, redirects to `/login?next=<pathname>`

Protected route prefixes:
```
/dashboard, /collabs, /campaigns, /jobs, /profile,
/earnings, /boost, /billing, /notifications, /settings,
/applications, /creators, /post-job, /admin
```

The session refresh happens on **all** requests, not just protected ones. This is intentional — Supabase JWT tokens need to be refreshed periodically and the middleware is the right place to do it.

### Row Level Security (RLS)

Every table has RLS enabled. Policies are defined in `supabase/migrations/001_initial_schema.sql`.

| Table | Read | Write |
|---|---|---|
| `users` | Own row only (`auth.uid() = id`) | Own row only |
| `brand_profiles` | Anyone (public read) | Own row only (`user_id = auth.uid()`) |
| `creator_profiles` | Anyone (public read) | Own row only (`user_id = auth.uid()`) |
| `campaigns` | Active campaigns (anyone); all for own brand | Own brand's campaigns only |
| `applications` | Creator: own; Brand: campaigns they own | Creator: insert own; Brand: update status on own campaigns |
| `collabs` | Both the creator and brand on the collab | Both parties |
| `submissions` | Both parties via their collab | Both parties |
| `live_posts` | Both parties via their collab | Both parties |
| `disputes` | Both parties via their collab | Both parties |
| `reviews` | Anyone (public read) | reviewer_id must equal auth.uid() |
| `notifications` | Own only (`user_id = auth.uid()`) | Own only |

**Important**: The admin dispute pages use `createAdminClient()` which bypasses RLS entirely — admin can read all disputes.

| Column | Type | Purpose |

**Status machine:**
```
briefed
  → (brand pays)
draft_submitted      ← creator submits draft
  → draft_approved   ← brand approves (or 48h auto-approve)
  → in_revision      ← brand requests revision (max 2)
  → disputed         ← either party raises dispute
draft_approved
  → live_submitted   ← creator submits live post URL
    → completed      ← brand confirms (or 72h auto-release)
    → disputed       ← either party raises dispute
disputed             ← admin resolves → completed or cancelled
completed            ← final state, payment released
cancelled            ← collab cancelled before draft_approved
```

**Note**: `live_confirmed` exists in the DB enum but the code uses `completed` directly when brand confirms a live post.

**RLS**: Both the creator_id and brand_id on the collab can read/write.

**Indexes**: `idx_collabs_creator`, `idx_collabs_brand`, `idx_collabs_status`

## 4. User Flows

### 4a. Brand onboarding

1. Brand lands on `/` and clicks "Post a campaign free" or "I'm a brand"
2. Redirected to `/signup?role=brand` — role toggle pre-selects "I'm a brand"
3. Brand enters company name, email, and password (min 8 chars)
4. Form POSTs to `POST /api/auth/signup` with `{email, password, name, role: 'brand'}`
5. Server calls `supabase.auth.signUp()` → session cookie set
6. Admin client inserts into `users` (`role='brand'`, `display_name=company_name`)
7. Admin client inserts into `brand_profiles` (`user_id`, `company_name`)
8. Welcome email sent fire-and-forget via `emails.welcomeBrand(name, email)`
9. Client receives `{success: true}` and router pushes to `/dashboard`
10. `/dashboard` renders `BrandDashboard` — shows stat cards and a "Post a campaign" CTA

### 4b. Creator onboarding

1. Creator clicks "Join as a creator" or "I'm a creator"
2. Redirected to `/signup?role=creator`
3. Creator enters name, email, password
4. POSTs to `POST /api/auth/signup` with `{role: 'creator'}`
5. Server inserts `users` row and an empty `creator_profiles` row (only `user_id` set)
6. Welcome email sent via `emails.welcomeCreator(name, email)`
7. Redirected to `/dashboard` → `CreatorDashboard` — shows "Browse campaigns" and "Edit profile" CTAs
8. Creator fills in their profile at `/profile` (bio, niches, base rate, platform handles/followers)
9. Profile saves directly to `creator_profiles` via `supabase.from('creator_profiles').update()`
10. Completion percentage shown: bio + niches + base_rate + platforms = 4 items, each 25%

### 4c. Brand posts a campaign

1. Brand goes to `/post-job` (client component)
2. Form fields:
   - **Required**: `title`, `brief`
   - **Required**: `comp_type` (paid / barter / both)
   - **Optional**: `budget_min`, `budget_max` (if paid), `barter_detail` (if barter)
   - **Optional**: `deliverable_types` (toggle chips)
   - **Optional**: `niche_tags` (toggle chips)
   - **Optional**: `min_followers`, `creators_needed`, `deadline`
3. Budget entered in SGD dollars; converted to cents on submit (`parseInt(value) * 100`)
4. POSTs to `POST /api/campaigns`
5. API checks free plan limit: max 2 active campaigns (returns 403 if exceeded)
6. Creates row in `campaigns` with `status: 'active'`
7. Campaign immediately visible on creator job board (`/jobs`)
8. `is_featured` defaults to `false` — featured campaign purchase pending

### 4d. Creator discovers and applies

1. Creator goes to `/jobs` — server component
2. All `status = 'active'` campaigns shown, ordered `is_featured DESC, created_at DESC`
3. Each card shows: brand name, title, comp_type badge, niche tags, budget range, deadline
4. Creator clicks a campaign → `/jobs/[id]`
5. Page shows: brand logo, title, badges, brief, deliverables, requirements, barter offer, escrow info callout (if paid)
6. If creator has already applied: shows application status; "View collab" link if selected
7. If not applied: shows `ApplyForm` component
8. In `ApplyForm`:
   - Pitch textarea (min 30 chars enforced)
   - Rate field (optional, in SGD dollars, converted to cents)
   - POSTs to `POST /api/applications`
9. API records whether creator's boost is active at submission time (`is_boosted = !!boost_active_until > now`)
10. Brand notified with in-app notification (`new_application`)
11. Duplicate application returns 409 "Already applied"

### 4e. Brand reviews applicants and selects

1. Brand goes to `/campaigns/[id]`
2. Stat cards show: Total / Pending / Shortlisted / Selected applicant counts
3. Applicant list ordered `is_boosted DESC, created_at ASC`
4. Free plan: only first 5 applicants visible; remaining shown as "X more hidden" with upgrade CTA
5. `ApplicantList` component (client) shows each applicant with:
   - Name, Verified badge, Boosted badge
   - Total follower count across platforms
   - Niches
   - Rating (if has reviews)
   - Pitch (2 lines clamped)
   - Proposed rate
6. Brand actions:
   - **Shortlist** → `PATCH /api/applications/[id]` with `{status: 'shortlisted'}` → creator notified
   - **Select** → `PATCH /api/applications/[id]` with `{status: 'selected'}` → collab created
   - **Pass** → `PATCH /api/applications/[id]` with `{status: 'rejected'}` → creator notified
7. On **Select**:
   - Application status updated to `'selected'`
   - `computeFee(proposed_rate, brand.plan)` calculates commission:
     - Free plan: `fee = agreed_rate * 0.12`, `payout = agreed_rate - fee`
     - Pro plan: `fee = agreed_rate * 0.08`, `payout = agreed_rate - fee`
   - New row inserted in `collabs` with `status: 'briefed'`
   - Creator notified: "You've been selected for [campaign]"
   - Response includes `{collab_id}` for routing

### 4f. Complete collab workflow

This is the most important flow. The collab object moves through a status machine.

**Step 1: briefed → brand deposits payment**

1. Brand goes to `/collabs/[id]`
2. `CollabActions` component shows: "Lock in escrow to start" if no payment intent yet
3. If creator has no `stripe_connect_id` (hasn't set up payouts), brand sees: "Waiting on creator — {name} hasn't connected a payout account yet"
4. Otherwise, brand sees `StripePaymentButton` (Apple Pay / Google Pay)
5. Button loads, POSTs to `POST /api/payments/create-intent` which:
   - Gets or creates a Stripe Customer for the brand
   - Creates `PaymentIntent` with `capture_method: 'manual'` (funds authorized but not captured)
   - Amount = `collab.agreed_rate` in SGD cents
   - Saves intent ID to `collabs.stripe_payment_intent_id`
   - Returns `{client_secret}`
6. Creator pays via Apple Pay / Google Pay — funds are **authorized** (held by Stripe, not yet captured)
7. Collab status stays `'briefed'` — payment held in escrow

**Step 2: draft_submitted**

8. Creator submits draft at `/collabs/[id]`
9. POSTs to `POST /api/collabs/[id]/submit-draft` with `{file_url, creator_note}`
10. New row in `submissions` (version auto-incremented)
11. `collabs.draft_auto_approve_at` = now + 48h
12. `collabs.status` → `'draft_submitted'`
13. Brand notified in-app and by email: "Draft submitted by [creator] — review it now (48h window)"

**Step 3: draft_submitted → brand reviews**

14. Brand reviews at `/collabs/[id]`
15. POSTs to `POST /api/collabs/[id]/review-draft` with `{decision, feedback}`
    - **`approved`**: `status → 'draft_approved'`, `draft_auto_approve_at` cleared, creator notified + emailed "Draft approved — post live now"
    - **`revision`**: Requires `feedback.length >= 20`. Increments `revision_count`. Max 2 revisions. `status → 'in_revision'`, creator notified with feedback text
    - **`rejected`**: Requires `feedback.length >= 20`. Submission marked rejected. Status stays `'draft_submitted'` — creator can accept or dispute

**Step 3a: 48h auto-approve (if brand doesn't review)**

- `auto-approve-drafts` cron (hourly) finds all `status = 'draft_submitted'` where `draft_auto_approve_at < now`
- Forces approval: `status → 'draft_approved'`, submission `decision → 'approved'`
- Both parties notified

**Step 4: draft_approved → creator posts live**

16. Creator posts content publicly on their platform
17. Returns to `/collabs/[id]`, submits live post URL
18. POSTs to `POST /api/collabs/[id]/submit-live` with `{post_url, screenshot_url?}`
19. New row in `live_posts`
20. `collabs.live_auto_release_at` = now + 72h
21. `collabs.status → 'live_submitted'`
22. Brand notified in-app and by email: "[Creator] posted live — confirm to release payment (72h)"

**Step 5: live_submitted → brand confirms**

23. Brand reviews the post at `/collabs/[id]`
24. Brand clicks "Confirm & release payment"
25. POSTs to `POST /api/collabs/[id]/confirm-live`
26. Server calls `stripe.paymentIntents.capture(intentId)` — funds captured from escrow
27. `live_posts.confirmed_at` set to now
28. `collabs.status → 'completed'`, `live_auto_release_at` cleared
29. `creator_profiles.collabs_completed += 1`, `creator_profiles.total_earned += creator_payout`
30. Creator notified in-app and by email: "[Amount] is on the way"

**Step 5a: 72h auto-release (if brand doesn't confirm)**

- `auto-release-live` cron (hourly) finds all `status = 'live_submitted'` where `live_auto_release_at < now`
- Calls `stripe.paymentIntents.capture()` first (non-fatal — error logged but flow continues)
- Updates `live_posts`, marks collab `completed`, updates creator stats
- Creator notified

**Step 6: Dispute path**

Either party can raise a dispute when status is: `live_submitted`, `draft_submitted`, `in_revision`, or `draft_approved`.

26a. Party POSTs to `POST /api/collabs/[id]/dispute` with `{reason, evidence_urls?}`
    - Reason must be ≥ 20 chars
    - `collabs.status → 'disputed'`
    - New row in `disputes` with `outcome: 'pending'`
    - Both parties notified in-app and by email

27a. Admin goes to `/admin/disputes` (admin role required)
28a. Sees all pending disputes, clicks into one
29a. `DisputeResolutionForm` with outcome options:
    - **creator_wins**: Stripe captures full amount, `collabs.status → 'completed'`
    - **brand_wins**: Stripe cancels intent (full refund), `collabs.status → 'cancelled'`
    - **split**: Captures `split_percentage`% of `agreed_rate`, `collabs.status → 'completed'`
    - **mutual**: Cancels intent, `collabs.status → 'cancelled'`
30a. Platform ruling written (required)
31a. Both parties notified: "Dispute resolved — [outcome]"

### 4g. Creator boost flow

1. Creator goes to `/boost`
2. Two options:
   - **Per application** (S$4): activates for 7 days
   - **Monthly** (S$20): activates for 30 days
3. Clicking "Buy" calls `POST /api/payments/boost-creator` with `{type: 'monthly' | 'per_app'}`
4. If boost is already active, days are **added** to existing expiry
5. `creator_profiles.boost_active_until` updated
6. **During beta**: boost activates immediately with no Stripe charge (Phase 6 TODO)
7. While boost is active:
   - Applications submitted include `is_boosted: true`
   - Creator appears with "Boosted" badge on applicant lists and creator directory
   - Applicant lists ordered `is_boosted DESC` — boosted creators shown first to brands
8. `expire-boosts` cron (midnight daily) clears expired `boost_active_until` values

### 4h. Rating flow

1. After a collab reaches `completed` status, either party can leave a review
2. `POST /api/reviews` with `{collab_id, rating, note?}`
   - `rating`: 1–5 (enforced by DB check constraint)
   - `reviewer_type` is set from the user's role
3. DB unique constraint `(collab_id, reviewer_type)` prevents double-rating
4. Reviews are publicly readable (creator profiles show brand reviews)
5. `update-ratings` cron (2am daily) recomputes `creator_profiles.rating_avg` and `rating_count` from all brand reviews

## 5. Payment Architecture

### 5a. Escrow flow step by step

| Step | What happens | Stripe state |
|---|---|---|
| Brand clicks "Lock in escrow" | `POST /api/payments/create-intent` creates PaymentIntent | `requires_payment_method` |
| Brand pays via Apple Pay / Google Pay | `stripe.confirmCardPayment()` with `handleActions: false` | `requires_capture` |
| Content workflow proceeds | Nothing — funds held | `requires_capture` |
| Brand confirms live post (or 72h passes) | `stripe.paymentIntents.capture(intentId)` | `succeeded` |
| Brand or admin cancels | `stripe.paymentIntents.cancel(intentId)` | `canceled` |

**What `capture_method: 'manual'` means**: Stripe authorizes the card (verifies funds are available and holds them) but does not move money. The money only moves when `capture()` is called. This is the escrow mechanism — brands can pay but creators only receive funds after delivery is confirmed.

**PaymentIntent parameters:**
```typescript
stripe.paymentIntents.create({
  amount: collab.agreed_rate,   // SGD cents
  currency: 'sgd',
  capture_method: 'manual',
  customer: customerId,
  payment_method_types: ['card'],
  metadata: { collab_id, creator_payout, platform_fee },
  description: `collabr. escrow — collab ${collab_id}`,
})
```

The `application_fee_amount` parameter (for splitting platform revenue via Stripe Connect) is not yet set — this will be added when Stripe Connect is fully wired.

### 5b. Commission calculation

Function: `lib/utils.ts:computeFee(rateCents, plan)`

```typescript
function computeFee(rateCents: number, plan: 'free' | 'pro') {
  const pct = plan === 'pro' ? 0.08 : 0.12
  const fee = Math.round(rateCents * pct)
  return { fee, payout: rateCents - fee }
}
```

Commission comes out of the creator's payout — it is not added on top of what the brand pays.

**Examples:**

| Deal | Plan | Brand pays | Platform fee | Creator receives |
|---|---|---|---|---|
| S$300 collab | Free | S$300 | S$36 (12%) | S$264 |
| S$300 collab | Pro | S$300 | S$24 (8%) | S$276 |
| S$150 collab | Free | S$150 | S$18 (12%) | S$132 |

These amounts are computed once when the collab is created (in `PATCH /api/applications/[id]` on select) and stored as `agreed_rate`, `platform_fee`, and `creator_payout` on the `collabs` row.

### 5c. Stripe Connect (pending full setup)

Stripe Connect Express allows creators to receive direct payouts to their Singapore bank accounts.

**Current state**: The API route `POST /api/stripe/connect` creates an Express account and returns an onboarding URL. The `ConnectOnboarding` component at `/earnings` surfaces this. However, `STRIPE_CONNECT_CLIENT_ID` is not yet configured in Vercel, and automatic payout transfers on capture are not yet wired.

**To complete setup:**
1. Get `STRIPE_CONNECT_CLIENT_ID` from Stripe Dashboard → Connect → Settings (starts with `ca_`)
2. Add to Vercel environment variables
3. When calling `stripe.paymentIntents.capture()`, add `transfer_data: { destination: creator.stripe_connect_id }` and `application_fee_amount: platform_fee`
4. Creator's `stripe_connect_id` is set in `creator_profiles` when onboarding completes

**During beta**: Payouts are handled manually via PayNow. When a collab completes, the platform pays the creator directly.

### 5d. Apple Pay / Google Pay

Handled entirely by `components/StripePaymentButton.tsx`. No extra configuration required — Stripe's Payment Request Button API auto-detects device capability.

Flow:
1. Component loads, calls `stripe.paymentRequest({ country: 'SG', currency: 'sgd', ... })`
2. `paymentRequest.canMakePayment()` — returns null if not available
3. If available: mounts `paymentRequestButton` element (shows Apple Pay or Google Pay button)
4. If not available: shows "Contact us" message (card/bank transfer fallback)
5. On payment: `stripe.confirmCardPayment(client_secret, { payment_method: ev.paymentMethod.id }, { handleActions: false })` — `handleActions: false` skips 3DS for wallet payments

### 5e. Barter campaigns

When `comp_type = 'barter'`:
- No Stripe PaymentIntent is created
- The agreed rate / escrow flow is skipped
- Brand pays a flat listing fee manually during beta (collected off-platform via PayNow)
- Barter listing fees (planned):
  - Nano (1–2 creators): S$15–25
  - Standard (3–5): S$40–60
  - Open call (5+): S$80–100
- The `ApplyForm` does not show a rate field for barter campaigns (`isPaid = comp_type !== 'barter'`)

## 8. Background Jobs (Cron)

Cron jobs are configured in `vercel.json` and run automatically on Vercel's infrastructure. All cron routes are protected with a `Authorization: Bearer <CRON_SECRET>` header.

### `GET /api/cron/auto-approve-drafts`

**Schedule**: `0 * * * *` (hourly, at :00)

**Why hourly**: Ensures draft auto-approval fires within 1 hour of the 48h window expiring. Tighter than daily but within Vercel Hobby plan limits.

**What it does:**
1. Queries all `collabs` where `status = 'draft_submitted'` AND `draft_auto_approve_at < now`
2. For each: updates `status → 'draft_approved'`, clears `draft_auto_approve_at`
3. Updates pending `submissions` row to `decision = 'approved'`
4. Notifies creator: "Draft auto-approved — post live now! (Brand did not respond in 48h)"
5. Notifies brand: "Draft auto-approved (You did not review within 48h)"
6. Returns `{processed: N}`

Uses `createAdminClient()` — no user session.

---

### `GET /api/cron/auto-release-live`

**Schedule**: `0 * * * *` (hourly, at :00)

**Why hourly**: Same as above — ensures auto-release fires within 1 hour of 72h window expiring.

**What it does:**
1. Queries all `collabs` where `status = 'live_submitted'` AND `live_auto_release_at < now`
2. For each:
   a. Attempts `stripe.paymentIntents.capture()` — non-fatal (error logged, flow continues)
   b. Marks `live_posts.confirmed_at = now`
   c. Updates `collabs.status → 'completed'`, clears `live_auto_release_at`
   d. Updates creator `collabs_completed++` and `total_earned += creator_payout`
   e. Notifies creator in-app: "[Amount] auto-released (Brand did not confirm within 72h)"
   f. Emails creator: payment released email
3. Returns `{processed: N}`

**Order matters**: Stripe capture happens first, then DB updates. If Stripe capture fails but is non-fatal, the collab is still marked complete (creator not penalized for Stripe issues).

---

### `GET /api/cron/notify-expiring`

**Schedule**: `0 9 * * *` (daily at 9am Singapore time)

**Why 9am**: Brands are awake and working — most likely to act on a reminder during the business day.

**What it does:**
1. Calculates `in6h` and `in12h` from now
2. Finds `draft_submitted` collabs where `draft_auto_approve_at` is between now and +6h
   - Sends in-app notification to brand: "Review pending: [campaign] auto-approves in <6h"
3. Finds `live_submitted` collabs where `live_auto_release_at` is between now and +12h
   - Sends in-app notification to brand: "Payment auto-releases in <12h for [creator]"
4. Returns `{notified_drafts: N, notified_live: N}`

---

### `GET /api/cron/expire-boosts`

**Schedule**: `0 0 * * *` (daily at midnight)

**What it does:**
1. Finds all `creator_profiles` where `boost_active_until < now` (and not null)
2. Sets `boost_active_until = null`
3. Returns `{expired: N}`

This is a cleanup job — the boost status is checked live throughout the app using `new Date(boost_active_until) > new Date()`, but nulling expired entries keeps the data clean.

---

### `GET /api/cron/update-ratings`

**Schedule**: `0 2 * * *` (daily at 2am)

**Why 2am**: Low traffic — safe for a full table scan.

**What it does:**
1. Fetches all `reviews` where `reviewer_type = 'brand'`, joining `collabs` to get `creator_id`
2. Groups ratings by creator
3. For each creator: recomputes `rating_avg = sum / count`, `rating_count = count`
4. Updates `creator_profiles` rows
5. Returns `{updated: N}`

**Note**: This recomputes from scratch on every run, not incrementally. Fine for current scale.

## 9. Business Rules

These are the enforced rules across the platform, with where each is enforced.

| # | Rule | Enforced in |
|---|---|---|
| 1 | Draft review window: 48h, then auto-approve | `auto-approve-drafts` cron; `draft_auto_approve_at` set in `submit-draft` route |
| 2 | Live post confirm window: 72h, then auto-release | `auto-release-live` cron; `live_auto_release_at` set in `submit-live` route |
| 3 | Max 2 revision rounds per collab | `review-draft` route: returns 400 if `revision_count >= 2` |
| 4 | Revision/rejection requires ≥20 character feedback | `review-draft` route: validates `feedback.length >= 20` |
| 5 | Dispute reason must be ≥20 characters | `dispute` route: validates `reason.length >= 20` |
| 6 | Cannot cancel after `draft_approved` | `cancel` route: only allows `briefed`, `draft_submitted`, `in_revision` |
| 7 | Cannot dispute before `draft_submitted` | `dispute` route: checks status is in `['live_submitted', 'draft_submitted', 'in_revision', 'draft_approved']` |
| 8 | Free plan: max 2 active campaigns | `POST /api/campaigns`: count check + 403 |
| 9 | Free plan: only first 5 applicants visible | `campaigns/[id]/page.tsx`: slices `visibleApps` to first 5 |
| 10 | Boosted creators appear first in applicant list | `campaigns/[id]/page.tsx`: orders by `is_boosted DESC` |
| 11 | Featured campaigns appear first in job board | `jobs/page.tsx` + `GET /api/campaigns`: orders by `is_featured DESC` |
| 12 | All monetary amounts stored as SGD cents (integers) | Enforced in UI forms (multiply by 100 before submit); `computeFee()` uses `Math.round()` |
| 13 | Commission deducted from creator, not added to brand | `computeFee()`: `payout = rate - fee` |
| 14 | Cannot apply twice to same campaign | DB unique constraint `(campaign_id, creator_id)`; `applications` route returns 409 |
| 15 | One review per collab per side | DB unique constraint `(collab_id, reviewer_type)` |
| 16 | `is_boosted` on application is set at submission time | `POST /api/applications`: checks `boost_active_until > now` at moment of insert |
| 17 | Only brand or creator on a collab can view/act on it | `collabs/[id]/page.tsx`: explicit user check; all collab routes verify party membership |
| 18 | Admin access requires `role = 'admin'` in users table | `admin/disputes` pages and all admin API routes check `profile.role !== 'admin'` |
| 19 | Signup email must be valid; password min 8 chars | HTML form validation; Supabase auth validates on signUp |
| 20 | Pitch must be at least 30 characters | `ApplyForm.tsx` client validation; server does not re-validate |

## 11. How to Run Locally

### Prerequisites

- Node.js 18+
- A Supabase project (or use the existing one)
- A Stripe account in test mode
- A Resend account (or skip — emails will log to console)

### Steps

1. **Clone the repo**
   ```bash
   git clone https://github.com/graccelim/collabr.git
   cd collabr
   ```

2. **Install dependencies**
   ```bash
   npm install
   ```

3. **Set up environment variables**
   ```bash
   cp .env.example .env.local
   ```
   Fill in `.env.local`:
   ```
   NEXT_PUBLIC_SUPABASE_URL=https://wfjmewmkiaaaqquuwmre.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=<get from Supabase → Settings → API>
   SUPABASE_SERVICE_ROLE_KEY=<get from Supabase → Settings → API>

   ```

   - Go to Supabase Dashboard → SQL Editor
   - Paste the contents of `supabase/migrations/001_initial_schema.sql`

## 12. Deployment

### Vercel

The app is deployed on Vercel (Hobby plan).

- **Auto-deploy**: Every `git push origin main` triggers a new production deployment
- **Build command**: `next build` (auto-detected by Vercel)
- **Output**: Static + serverless functions (all pages are server-rendered on demand)
- **Cron jobs**: Configured in `vercel.json`, automatically scheduled by Vercel

### Vercel environment variables

Set all variables from section 2 in Vercel Dashboard → Project → Settings → Environment Variables. Apply to Production, Preview, and Development environments as appropriate.

### Cron schedule (`vercel.json`)

```json
{
  "crons": [
    { "path": "/api/cron/auto-approve-drafts", "schedule": "0 9 * * *" },
    { "path": "/api/cron/auto-release-live",   "schedule": "0 10 * * *" },
    { "path": "/api/cron/notify-expiring",     "schedule": "0 8 * * *" },
    { "path": "/api/cron/expire-boosts",       "schedule": "0 0 * * *" },
    { "path": "/api/cron/update-ratings",      "schedule": "0 2 * * *" }
  ]
}
```

**Note on Vercel Hobby plan**: The Hobby plan only supports daily cron invocations. `auto-approve-drafts` runs at 9am and `auto-release-live` at 10am daily (SGT). This means auto-approvals and auto-releases can fire up to ~24h late relative to the 48h/72h deadline. Upgrade to Vercel Pro to run these hourly for tighter enforcement of the windows.

### Custom domain

When collabr.sg is registered:
1. Go to Vercel → Project → Settings → Domains
2. Add `collabr.sg` and `www.collabr.sg`
3. Update DNS records at domain registrar with Vercel's CNAME/A records
4. Update `NEXT_PUBLIC_APP_URL` in Vercel environment variables to `https://collabr.sg`

### Supabase Storage

The `brand-assets` bucket in Supabase Storage stores brand logos. It must be created manually:
1. Go to Supabase Dashboard → Storage → New bucket
2. Name: `brand-assets`
3. Make it **public** (logos need to be accessible via public URL)

### Next.js image domain configuration

`next.config.js` allows images from the Supabase project and Google (for avatar URLs):
```javascript
images: {
  remotePatterns: [
    { protocol: 'https', hostname: 'wfjmewmkiaaaqquuwmre.supabase.co' },
    { protocol: 'https', hostname: 'lh3.googleusercontent.com' },
  ],
}
```

If you add other image sources (e.g. Cloudinary, a CDN), add them here.
